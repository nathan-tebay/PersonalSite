PersonalSite

This site — a hand-rolled portfolio, project archive, CMS, and Lambda-hosted deployment target built without a frontend framework

View on GitHub

Overview

PersonalSite started as a constraint-driven portfolio rebuild: no frontend framework, no Node runtime, no build step, and no heavyweight CMS. It has since become the operating surface for tebay.dev: project documentation, a blog, a curated links page, an admin panel, deployment scripts, smoke checks, and a small analytics pipeline.

The public side is still plain HTML, CSS, and vanilla JavaScript. Shared navigation is injected by assets/layout.js, project metadata lives in assets/project-data.js, and page-specific scripts render blog posts, links, and theme state without a bundler. The admin side is implemented as POSIX shell CGI scripts behind cookie-based session auth.

Production runs as an AWS Lambda container behind CloudFront. BusyBox httpd serves from /tmp/www, the AWS Lambda Web Adapter bridges Lambda events to HTTP on port 8080, and S3 stores blog posts, images, links, and analytics data. On cold start the container syncs S3 content into a local cache so normal page reads stay fast and simple.

Current Status

  • Live at tebay.dev with project pages, responsive navigation, persistent theme swatches, blog rendering, links rendering, and an admin panel.
  • Blog and links content are managed through CGI endpoints and mirrored between S3 and the Lambda-local cache for immediate reads after writes.
  • Admin workflows include login/logout, draft save, publish, delete, image upload/list/delete, link management, and analytics review.
  • Deployment is scripted: deploy-lambda.sh builds a linux/amd64 container with Podman, pushes to ECR, updates the Lambda function, waits for completion, and reports the resolved image digest.
  • Validation is split between static site checks (validate-site.py) and production smoke checks (smoke-check.sh https://tebay.dev).

Design Constraints

  • Use no frontend frameworks, libraries, or build tools — just plain HTML, CSS, and JavaScript.
  • Keep the runtime small and transparent: BusyBox httpd, shell CGI, AWS CLI, and the Lambda Web Adapter.
  • Support local development with Podman and MinIO while keeping production storage on AWS S3.
  • Make publishing possible from the site itself without adding a database server, Node application, or external CMS.
  • Keep deployment repeatable enough that production fixes can be built, pushed, and verified from one script.

AI-Assisted Build

I used Claude Code heavily while designing, implementing, and documenting the site. That was useful for quickly iterating on CGI scripts, Dockerfiles, AWS setup, admin UI, and validation tooling, but it also exposed places where AI needs tight supervision:

  • It was effective at generating small, testable shell and frontend changes when the constraints were explicit.
  • It tended to confuse BusyBox httpd, Apache-style CGI assumptions, Lambda filesystem limits, and auth/session edge cases unless corrected with real runtime feedback.
  • It was most valuable as a fast implementation partner, not as an autopilot. The important work was constraining the design, reading the generated code, and verifying behavior in the real deployment environment.

Challenges

  • Lambda's read-only filesystem means the image web root cannot be modified in place. Startup copies the site to /tmp/www, then httpd serves from there so posts, manifests, links, and generated CGI files can be updated.
  • Lambda containers need the AWS Lambda Web Adapter. A Dockerfile refactor accidentally removed the adapter copy and PORT=8080, which produced production 502 responses until the adapter layer and readiness timeout were restored.
  • Third-party S3 clients and Lambda temporary credentials were brittle in this environment. The production image uses AWS CLI despite the size cost because it reliably follows the standard credential chain.
  • The first request after a cold start depends on content availability. The entrypoint performs a synchronous S3 sync before starting httpd, then refreshes the cache in the background every 10 minutes.
  • Shell-based JSON handling is fragile. Manifest updates use small line-oriented helpers, advisory locks in /tmp, and explicit cleanup of leading commas before re-inserting entries.
  • Lambda CPU is proportional to memory. Too little memory looked like AWS CLI/network slowness rather than an obvious resource issue.

Learnings

  • Lambda plus CGI is viable for a low-traffic personal site: each request is isolated, the runtime is understandable, and persistence can be pushed to S3.
  • Cold-start behavior matters more than steady-state behavior. The site needs placeholder manifests, synchronous startup sync, and smoke checks because a broken cold start looks like a broken website.
  • A local MinIO-backed dev environment is worth the setup. It lets the same storage code path run locally without touching production S3.
  • Static validation catches broken links and markup, but the deployment surface also needs live route checks because CloudFront, Lambda, ECR, and the adapter can fail independently of the HTML.
  • Keeping the frontend framework-free made the project easier to reason about. Most complexity lives where it belongs: storage, auth, deployment, and Lambda startup behavior.

Key Features

  • Shared layout script injects responsive navigation and keeps project pages consistent without a build step.
  • Multi-theme color picker derives readable text/link colors from selected swatches and persists the choice in localStorage.
  • Blog CMS supports drafts, publishing, WIP placeholders, per-post images, public manifests, and admin-only manifests.
  • Links CMS manages categorized bookmark cards through the same admin surface.
  • Cookie-based admin session auth with shared session utilities, refresh timestamps, and rate limiting helpers.
  • Lightweight analytics beacon logs privacy-truncated IP, page/referrer/user-agent, optional geo data, and admin-only JSON reporting.
  • Production deployment script handles ECR login, no-cache linux/amd64 image build, push, Lambda update, waiter, and deployed digest reporting.
  • Static validation and live smoke checks cover the homepage, project pages, blog manifests, links, and admin route.
