The Dual Key Database

A story about the pitfalls of a database design where the main tables had dual keys based on a type identifier, and how one early decision compounded for fifteen years.

Nathan Tebay · March 2026

I once worked with a database that violated relational database standards, causing a lot of headaches for developers due to a single design decision. For 15 years, this had been the underpinnings of a monolithic web application that grew on the whims of client desires and developers' fancy. The main table held objects, with object_id as its primary key, a type field that could take one of 5 types, and id fields for each type. That type and populated ID field determined which fields were required and what tables were related. This design caused several problems that developers had to account for in the business logic, because foreign keys did not function as expected. Increasing knowledge is needed to implement simple CRUD operations and to improve the database performance in various ways.

The main drawback of this design came from the ways it broke the relational database model. Database features such as cascading deletes and foreign keys were replaced with complex stored procedures or implemented in business logic, increasing maintenance overhead and making the phrase 'technical debt' all too common. Add to that multiple paths to interact with the database, a VB.NET-based BLL/DLL implementation for the main application, an API implemented as a POC for one section of the product, and multiple supporting products with their own implementations at different times, and implementing new features always came with a longer timeline than seemed reasonable. This single database design decision, while not wholly responsible for the technical debt, was a major contributor to it.

So why not fix it? How to fix it was often discussed amongst our small development team, and it was actually very doable at the database level.

The more challenging part was the six+ month timeline on rewriting every flow that touched the database and the high-level risk of data corruption. These changes were not an option when new features in our sprawling multi-tenant application were important to keeping clients happy and revenue flowing.

It was a bit of a catch-22: stop new feature implementations at the risk of losing client revenue, or continue the way it had been for years — continuing to add more to an already bloated application that had been growing for over a decade to provide more value to clients looking to get all they could out of a niche, expensive tool. The business needs to keep momentum, which will always trump refactoring a functional, albeit sub-optimal, system design.

I don't write this to complain about or belittle anyone involved in bringing this design to life. In this case, it was someone learning as they went, making decisions that made sense at the time. They built an impressive business over the course of a decade. Many developers had a hand in building the product over the years. As the product's feature set grew around this core decision, many mitigations were implemented, often based on developers' skill sets, to overcome its shortcomings. I want to show how something simple can have long-term impacts on the product, development team, and the company as it compounds over time.

Early design decisions compound — plan for the system you'll have in ten years, not the one you have today.
A schema that works for an MVP can become unmaintainable at scale. Violating relational database constraints to save time upfront transfers that cost to every developer who touches the codebase afterward, multiplied across every year the system runs.
