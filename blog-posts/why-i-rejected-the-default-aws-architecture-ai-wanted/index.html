Why I Rejected the "Default" AWS Architecture AI Wanted

AI always reaches for the same AWS blueprint. On QMK Nexus, that blueprint was wrong — and knowing why required domain knowledge no prompt can replicate.

Nathan Tebay · May 2026

One thing I've learned building with AI is that it always leans toward the standard architecture.

If you ask an AI model to build an AWS application, you will almost always get some variation of:

  • API Gateway
  • Lambda
  • DynamoDB
  • S3 for assets
  • Standard framework boilerplate

That setup works for many projects.

It didn't work for QMK Nexus.

QMK Nexus generates QMK firmware for custom keyboards. That means dealing with big firmware definitions, compiler toolchains, MCU quirks, and long-running builds.

The default AI-generated architecture fell apart fast under those constraints.

For example, AI consistently pushed toward DynamoDB for keyboard indexing. I rejected that for several reasons:

  • 400KB item size limits become problematic with firmware metadata
  • Full-text style search is awkward
  • The data behaves more like files than relational entities

S3 with in-memory indexing was simpler and better suited to the workload.

The same thing happened with firmware builds.

AI kept suggesting Lambda because that's the standard AWS serverless answer. But avr-gcc and arm-gcc builds are CPU-heavy and sometimes take a while. Lambda limits quickly become operational constraints.

So I moved the build system to ECS Fargate instead.

I also avoided depending on the QMK CLI. Instead of wrapping the existing toolchain, qmk-nexus generates firmware configs directly in Python.

That's a lot harder to build, but it's also much easier to control.

This is where AI-assisted engineering actually gets interesting.

The leverage isn't in taking AI's first suggestion. It's in knowing the problem domain well enough to spot when the default answer is wrong.
